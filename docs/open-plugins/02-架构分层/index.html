    02 · 架构分层：四个核心模块如何分工与协作¶

    2.1 总览¶

    OpenPlugins 的代码被清晰地切成若干模块，按职责可以归为一条主链（运行时）、一套 SDK（面向开发者）与一堆支撑库（横切能力）。

                    ┌─────────────────────────────────────────────┐
                │  主程序 / 宿主应用 (AnycubicSlicerNext)      │
                └──────────────────┬──────────────────────────┘
                                   │ SetupPM / ShutdownPM / EmitEvent
                ┌──────────────────▼──────────────────────────┐
                │  plugins_manager  插件运行时核心             │
                │  · 包校验 / 解压 / 加载 / 生命周期           │
                │  · 依赖解析 / 函数路由(EventRouter)          │
                │  · XRC 界面 / 内存文件系统 / 配置 / i18n 接入 │
                └───────┬──────────────────────────▲──────────┘
                        │ 继承实现 PluginHost        │ 调用 Router
            ┌───────────▼──────────┐     ┌──────────┴─────────────┐
            │  plugins_base        │     │  plugins_sdk           │
            │  · 接口契约/元数据   │     │  · event 事件系统      │
            │  · IStream/OStream   │     │  · webview Web API     │
            │  · 函数包装/序列化   │     │  · constant/communication│
            └──────────────────────┘     └────────────────────────┘

    支撑库：utility（编解码/加密/JSON/文件）、easy_log（日志）、WebView（wxWebView 封装）、instrument（符号化）、resources、3rdparty。

    2.2 分层职责¶

    2.2.1 plugins_base —— 契约层（被所有模块依赖）¶

    这是插件的"法律条文"，只定义接口与基础数据结构，几乎不依赖 GUI（仅前向声明 wxEvtHandler 等）。包含：

    • plugins.hxx：核心接口 Plugin、PluginBase、PluginHost、PluginRouter、RequestHandler；
    • plugins_base.hxx：PluginInfo 元数据 + PLUGIN_EXPORT_GETINFO/PLUGIN_EXPORT_SETUP C ABI 导出宏；
    • plugins_stream.hxx：内存流 IStream/OStream（插件间通信的载体）；
    • funcation.hxx + function_traits.hxx + pack.hxx：成员函数 → 请求处理器的模板包装、参数序列化；
    • i18n.hxx / i18n_helper.hxx：翻译宏与翻译文件打包支持；
    • tuple_foreach.hxx：元组遍历辅助。

    关键设计：契约层不持有任何"实现"。管理器（插件宿主）会 继承 PluginHost，插件会 继承 Plugin，但二者只通过 plugins_base 的纯接口相遇，互不包含头文件依赖对方的实现。

    2.2.2 plugins_manager —— 运行时核心¶

    这是整个框架的"引擎"，同时扮演两个角色：

    1. PluginsManager 接口（对外）：AddWidget、AddStaticPlugins、SetConfig、EmitEvent、ExecuteFunction、包遍历/查询；
    2. PluginHost 实现（对插件）：Router()、HasPlugin/GetPlugin、GetWindow/WatchWindow、CreatePanel、Language/LoadTranslation、AddFS/DelFS、GetValue/SetValue（含加密配置）、Free。

    内部实现 PluginsManagerImpl（detail/plugins_manager_impl.{hpp,cpp}）同时继承这两个接口，是"管理器的门面 + 插件的宿主"。其内部构件：

    内部组件 文件 职责
    LibraryBase / LibraryShared / LibraryStatic detail/LibraryBase.* 动态库（wxDynamicLibrary）与静态库的统一抽象，暴露 GetPluginInfo/SetupPlugin
    EventRouter detail/router.* 全局函数路由表，key 为 插件名/函数名
    package.* detail/package.* 插件包：Zip/Unzip、签名 signature.bin 的 AES 加解密、MD5 校验、包信息解析
    MemoryFSHandler detail/fshandler.* 内存虚拟文件系统，为 XRC 界面提供 acmemory: 资源
    xh_webview detail/xrc/xh_webview.* wxWebView 的 XRC 处理器（让界面定义里能写 WebView）
    tranclations detail/tranclations.* i18n 框架接入（基于 acTranslationsLoader）

    2.2.3 plugins_sdk —— 开发者 SDK¶

    面向"写插件的人"提供能力封装：

    • event/：wxPluginEvent（wxNotifyEvent 子类）——通用事件包装，支持键值对、共享数据指针、状态/错误码；
    • webview/：WebviewApiHandler、RouterBase、InstanceBase、资源/脚本处理——把 C++ 成员函数暴露成 Web API；
    • constant/：配置常量；
    • communication/：widget_types.* 通信相关类型定义。

    2.2.4 支撑库¶

    模块 职责 关键技术
    utility 编解码（md5/base64/bin2ascii）、加密（AES/RSA）、JSON、文件、字符串、查询解析 OpenSSL EVP、自实现轻量工具
    easy_log 分级日志 + 调用栈 spdlog（daily/console/UDP sink）、栈回溯
    WebView wxWebView 跨平台组件 Windows: Edge(WebView2)/IE；macOS: WebKit/Chromium；GTK: WebKit2
    instrument 崩溃堆栈符号化 msw/unix 平台实现
    resources 公共资源定义 common.hxx

    2.3 模块依赖方向（关键约束）¶

    从 CMakeLists.txt 与头文件 include 关系可以归纳出清晰的依赖规则：

    1. plugins_base 是最底层，不依赖 plugins_manager/plugins_sdk；
    2. plugins_manager 依赖 plugins_base（实现 PluginHost 需要 Plugin 接口），并通过 library 链到插件库；manager 还 find_package(wxWidgets 3.3 CONFIG)，link wxWidgets 与 CURL；
    3. plugins_sdk 面向插件侧，依赖 plugins_base 的流/接口约定，但不反向依赖 manager（插件拿到 PluginHost* 之后由 host 代为执行能力）；
    4. 所有插件（plugins/* 测试插件）通过 add_static_plugin / add_shared_plugin 挂到 PM_DEPS，动态插件输出名 plugin_<name>，静态插件被编译进 manager（PLUGINS_LIST_SIZE）。
    # plugins_manager/CMakeLists.txt 片段：静态插件如何进入运行时
set(gen_embed_file_header ${CMAKE_CURRENT_BINARY_DIR}/plugins_list.h)
file(WRITE ${gen_embed_file_header} "#define PLUGINS_LIST (")
if(DEFINED PM_DEPS)
    foreach(item ${PM_DEPS})
        file(APPEND ${gen_embed_file_header} "${item},")
    endforeach()
endif()
file(APPEND ${gen_embed_file_header} "NONE)\n")
list(LENGTH PM_DEPS PLUGINS_LIST_SIZE)

    也就是说：静态插件（随主程序一起发布）由 CMake 在编译期收集进 plugins_list.h，运行期 PLUGINS_LIST_SIZE>0 时通过 GetCreateLibraryArray() 批量注册（见第 4 章）；而 PM_DEPS 列表就是"编译进 manager 的静态插件清单"。

    2.4 一个贯穿性的概念：宿主-插件双接口¶

    整个框架的核心关系是双向约定：

             plugins_base 定义的纯接口
   ┌─────────────────────────────────────┐
   │   Plugin（插件必须实现）            │
   │   PluginHost（宿主必须实现）        │
   │   PluginRouter（路由表）            │
   │   RequestHandler（函数处理器）      │
   └─────────────────────────────────────┘
          ▲                    ▲
   PluginsManagerImpl    任意业务插件
   （实现 PluginHost）   （实现 Plugin）
    • 宿主（PluginsManagerImpl）向插件提供：路由、窗口、面板、翻译、虚拟文件系统、配置——对应 PluginHost 的十几个纯虚方法；
    • 插件向宿主提供：生命周期方法 + 若干注册进路由的函数——对应 Plugin 接口与 REGISTER_FUNCATION 注册。

    这套"双接口 + 纯虚契约"设计，让主程序与插件各自独立演进，也保证了插件可以跨二进制边界（动态库）安全调用宿主能力。

    本章要点¶

    • 四个核心模块各司其职：base=契约、manager=运行时、sdk=开发者能力、utility/easy_log/WebView=横切支撑；
    • 依赖方向单向：base ← manager/sdk，manager 与 sdk 不互相反向依赖；
    • 关键的双接口模型：PluginsManagerImpl 同时是"管理器门面"和"插件宿主"；
    • 静态插件由 CMake 编译期收集（PM_DEPS → plugins_list.h → PLUGINS_LIST_SIZE）。

    代码定位¶

    • 顶层装配：CMakeLists.txt
    • manager 双接口：plugins_manager/plugins_manager.hxx、plugins_manager/detail/plugins_manager_impl.hpp
    • 静态插件收集：plugins_manager/CMakeLists.txt、plugins/CMakeLists.txt
