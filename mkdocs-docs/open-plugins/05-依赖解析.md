# 05 · 依赖解析：多轮迭代与循环依赖处理

插件之间不是孤岛。一个插件可能需要调用另一个插件注册的函数（例如 `address` 依赖 `utility`），因此**实例化顺序必须满足依赖关系**。本章讲解 OpenPlugins 如何用"多轮迭代"解析插件依赖 DAG，以及如何面对循环依赖。

## 5.1 依赖从哪来

依赖在 `PluginInfo` 里显式声明：

```cpp
static const char *depends[] = {"utility"};           // 依赖的插件名
static PluginInfo info{
    .plugin_api = 1,
    .dependency_count = sizeof(depends) / sizeof(depends[0]), // 依赖个数
    .dependency = depends,
    ...
};
```

宿主在 `InitPlugin` 里逐条检查"被依赖的插件是否已存在"：

```cpp
for (auto idx = 0; idx < info->dependency_count; idx++) {
  if (!HasPlugin(info->dependency[idx])) {       // 依赖未加载
    return false;
  }
}
// 依赖全部满足，才 SetPluginName + SetupPlugin
```

`HasPlugin` 的实现是在 `instances_`（已实例化的插件列表）里按名字查找：

```cpp
bool PluginsManagerImpl::HasPlugin(const char *name) {
  auto n = wxString::FromUTF8(name);
  return std::ranges::find_if(instances_, [n](const auto &pair) {
           return pair.first == n;
         }) != std::end(instances_);
}
```

注意：**依赖判定的粒度是"插件实例是否已创建"**（`instances_`），而不是"库是否已装载"（`libraries_`）。也就是说，A 依赖 B，必须等 B 真正实例化成功、注册完函数，A 才能被实例化。

## 5.2 多轮迭代：按拓扑序逐步"解锁"

由于 `InitPlugin` 是"整库整库"地判断，而插件之间可能存在链式依赖（A→B→C），OpenPlugins 采用**轮次扫描**策略：

```cpp
void PluginsManagerImpl::CreateInstances(void) {
  std::vector<std::shared_ptr<LibraryBase>> libraries;
  std::swap(libraries_, libraries);          // 取出待初始化列表
  do {
    previous_size = 0;
    for (auto itr = libraries.begin(); itr != libraries.end();) {
      auto lib = *itr;
      if (InitPlugin(lib)) {                 // 本轮依赖满足 → 实例化
        libraries_.push_back(lib);
        itr = libraries.erase(itr);
        previous_size += 1;
      } else {
        ++itr;                               // 未满足 → 留到下一轮
      }
    }
  } while (previous_size > 0 && !libraries.empty());
}
```

过程可以形象地理解成**逐轮"解锁"**：

```
第 0 轮：扫描全部库，凡是"零依赖或依赖已满足"的 → 实例化并移出
第 1 轮：剩余库中，依赖上一轮实例的 → 现在满足了 → 实例化并移出
第 2 轮：继续……
直到 某一轮没有任何进展（previous_size == 0）或 列表清空
```

举例（三个插件）：
- 第 0 轮：`C`（无依赖）实例化 → `instances_={C}`；
- 第 1 轮：`B`（依赖 C）实例化 → `instances_={C,B}`；
- 第 2 轮：`A`（依赖 B）实例化 → `instances_={C,B,A}`；
- 列表清空，结束。

## 5.3 循环依赖：明确报错而非死循环

多轮迭代最怕的就是**互相依赖**（A 依赖 B、B 依赖 A），这样任何一轮都不会有进展。OpenPlugins 的退出条件正好兜住了这个坑：

```cpp
} while (previous_size > 0 && !libraries.empty());

LOG_ERROR_IF(!libraries.empty(), "未解决的循环依赖，剩余库: {}", libraries.size());
```

- 当某轮 `previous_size == 0`（没有任何库能实例化）但 `libraries` 仍非空时，循环退出；
- 此时剩余库要么是**循环依赖**，要么依赖了**根本不存在的插件**，统一以 `LOG_ERROR` 记录"未解决的循环依赖，剩余库 N"。

这个设计很务实：**不会因循环依赖而死循环，也不会静默吞掉**，而是以一条错误日志暴露问题，同时让其余正常插件继续运行。代价是——循环依赖里的插件最终都不会被加载。

## 5.4 依赖解析 + 路由注册的顺序保证

依赖解析和函数路由注册是联动的。插件在构造函数里通过 `host_->Router()` 注册函数（见第 6 章 `REGISTER_FUNCATION`），而构造函数由 `lib->SetupPlugin(this)` 触发。所以：

```
某插件实例化的那一刻 ⇒ 它的构造函数跑完 ⇒ 它的函数已注册进 EventRouter
⇒ 之后任何"依赖它的插件"实例化时，就能安全调用它的函数
```

这正是为什么依赖检查要以 `instances_` 为粒度——**"实例已创建"隐含"函数已注册"**，从而保证跨插件函数调用不会命中未注册的符号。

## 5.5 实例的逆序销毁

与"依赖先满足者先实例化"的升序相反，销毁按**逆序**执行（`kEventExitByGUI`）：

```cpp
std::for_each(instances_.rbegin(), instances_.rend(),
              [](auto &pair) { pair.second->Stop(); });
```

`instances_` 是 `std::vector`，后实例化的在末尾。逆序遍历即"后初始化的先 Stop"，天然满足依赖的反向释放：先停上层插件（它们依赖下层），再停下层插件（它们被上层依赖）。

## 5.6 局限与思考

1. **依赖在初始化时一次性判定**：依赖关系只在 `InitPlugin` 时检查，插件运行期无法"新增依赖"——这是合理的静态契约约束；
2. **依赖名必须精确匹配**：`HasPlugin` 是字符串精确匹配，插件名拼写不一致会导致"依赖未找到"；
3. **循环依赖 = 不加载**：报错但跳过，不会做更复杂的解环；
4. **与包级依赖的区别**：`PluginInfo.dependency` 是插件级依赖；插件包（zip）之间则没有显式依赖声明（但 `address` 示例里 `depends={"utility"}` 表明插件级依赖足够表达跨包依赖）。

## 本章要点

- 依赖在 `PluginInfo.dependency` 声明，宿主用 `HasPlugin`（按实例名）逐条检查；
- 实例化采用**多轮迭代扫描**：每轮把"依赖已满足"的插件移出待初始化列表，直到无进展或清空；
- 循环依赖由退出条件 `previous_size == 0` 兜底，以 `LOG_ERROR` 暴露，剩余插件不加载；
- 实例化顺序天然保证"先实例化者函数已注册"，跨插件调用安全；
- 销毁按实例列表逆序 Stop，符合依赖反向释放。
